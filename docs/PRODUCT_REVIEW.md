**Flow 产品定位与系统设计审查 · 2026-10-18**

后续实施已加入新版定义语义、固定依赖/执行上下文、持久信号 inbox、受限业务入口、原生模型节点、离线证据包、历史驱动 regression 和复制升级工具。当前可用合同见 [EXECUTION.md](EXECUTION.md)；下文保留审查时的事实与任务依据。

审查对象是当前工作区，包括尚未提交的 SQLite 存储与事实校验修改。本文给出设计评审和实施任务，没有实施这些重构。P1 表示阻碍下文对应产品承诺；其中既有能力缺口，也有已有执行契约与目标业务不匹配的情况，不把所有缺口都称为实现 bug。

**【品味评分】凑合，持久化和副作用边界有好品味。**

单一 reducer、事实与当前状态原子提交、执行器进程隔离、授权先于外部操作、未知结果等待裁决，都应该保留。薄弱处是产品承诺超出了当前执行模型：恢复不等于复现，记录 stdout 不等于记录 agent 的每一步，异步触发入口不等于完整业务 API。

**【核心判断】值得做；保留底座，补齐执行契约，无须整套推倒。**

建议定位为：**以持久化执行事实为核心、支持人工介入与历史回归的业务工作流引擎，可以编排 API、脚本和 LLM，并将流程暴露为可调用的业务能力。**

MVP、POC、回归、生产业务是同一套流程资产的使用阶段。最有价值的闭环是“做出流程 → 运行真实请求 → 从运行记录提取用例 → 修改流程 → 比较差异 → 发布”。这是一项产品方向判断，不是市场需求已经验证的结论。

JSONL 应当是稳定的交换、查看、分析格式。当前权威存储实际是 SQLite。为了满足上述定位，不需要把它改回文本文件，也不需要另外追加一份必须同步成功的 JSONL 权威账本。两个提交点只会重新制造一致性问题。

**【关键洞察】**

- 数据结构：核心关系是不可变流程版本、一次运行、节点执行、尝试、外部操作、输入输出正文和历史来源关系。日志的价值来自这些关系与完整证据，换行分隔 JSON 本身不提供这些语义。
- 复杂度：保留一个状态转移实现；正式运行、恢复和回归共用节点语义，通过执行边界选择真实外部调用或录制结果。
- 风险点：将“重新执行”当成“恢复”，以及将未选分支当成失败传播，会直接改变业务行为。

**目前能够承诺的范围**

| 目标 | 当前判断 | 实际边界 |
| --- | --- | --- |
| MVP / POC | 可以作为基础 | 适合有限 DAG、受信任使用者、可接受当前容量和部署边界的场景 |
| 崩溃后继续 | 已有实质能力 | 从已提交状态继续；已授权但无结果的操作等待裁决 |
| 过程可追溯 | 节点层基本具备 | observations 可以丢弃；harness 内部调用没有结构化的逐步执行契约 |
| 还原历史状态 | 有离线校验能力 | `projection_check` 重放事实比较当前行，不重新执行脚本 |
| 相同条件重新计算 | 不具备完整保证 | JS 时间/随机数、子流程版本与执行器环境没有全部固定 |
| 基于历史运行做 regression | 缺少产品闭环 | 现有 API 没有 baseline、fork、fixture 匹配、候选运行差异报告 |
| 前端调用业务流程 | 异步创建 run 已支持 | 结果查询/订阅另走 RPC；入口凭据没有按业务调用者和 run 授权 |
| 一般业务编排 | 部分满足 | 分支合流、错误处理、异步事件竞态需要补齐；当前不是通用循环模型 |
| HA | 未提供 | 远程 agent 扩算力，注册表不复制业务状态、不接管 run |

**【致命问题与改进方向】**

**1. P1：普通 if/else 合流会被跳过，还能报告成功。**

证据：[incoming_gate](../crates/flow-backend/src/journal_driver.rs#L546)、[settle_run](../crates/flow-backend/src/journal_driver.rs#L707)。任一前驱 `Skipped` 都令整个目标节点 `Skip`；未选分支产生的跳过会一直传播到公共后续节点。收尾阶段只检查是否存在失败节点，允许所有 end 都被跳过后得到成功和空输出。

独立探针运行了 `start → condition(true) → a/b → merge → end`。结果：

```json
{"run_status":"succeeded","merge_status":"skipped","merge_reason":"upstream_skipped","end_status":"skipped","output":{"type":"inline","value":null}}
```

这是当前 AND 入边契约的实际行为，已有单测也在保护该行为；但它不能直接承担一般业务的条件分支合流。

修复方向：显式表达 join 策略和依赖满足状态。最低限度区分“必须全部成功”和“等待所有入边确定后，接受已选分支的成功结果”；未选分支是 inactive，失败是 failed，不能统一折成一种 skipped。后者不是“第一个成功就提前跑”。全部 inactive 应传播 inactive，失败如何处理由策略明确规定。增加公共出口是否真正执行的验收。

不要把全局 AND 直接改成 OR，那会破坏现有并行依赖。新行为通过定义语义版本或显式 join 配置引入。

**2. P1：当前的事实回放，不是用户需要的回归执行。**

证据：[事实校验器](../crates/flow-backend/src/projection_check.rs#L40)、[reducer](../crates/flow-engine/src/journal_state.rs#L1)、[RPC 方法目录](../crates/flow-rpc/src/journal_v2.rs#L256)。前者验证已有事实还原出的行是否一致；没有执行候选流程、比较新旧行为的接口。

需要把四种操作分开定义：

| 操作 | 输入与行为 | 是否调用外部系统 |
| --- | --- | --- |
| 历史还原 | 读取已有事实、结果和信号，还原已发生的过程 | 否 |
| 恢复继续 | 同一个 run 从已提交状态继续未完成工作 | 由已授权操作状态及执行策略决定 |
| 回归执行 | 新 run，执行候选定义；外部依赖由明确的 fixtures 提供 | 默认否 |
| 再次真实运行 | 新 run，重新执行指定流程 | 是，可能再次产生业务效果与费用 |

HTTP/LLM 请求已经改变时，不能偷偷把旧响应塞进去并声称已验证新请求。回归必须严格匹配请求摘要，或者显示声明替代 fixture；需要验证新模型时，另建允许指定模型调用的 live evaluation，其他业务副作用仍受限。

这不是照搬另一套引擎的要求。Temporal 对历史回放也明确区分重新执行编排和复用已记录的外部操作结果：[官方说明](https://docs.temporal.io/workflows)。Flow 可以继续采用 DAG 与 reducer 的现有方案。

**3. P1：流程版本固定了，依赖与运行环境还没有固定。**

证据：[子流程创建](../crates/flow-backend/src/execution/dispatch.rs#L930)在调用时选择最新已发布版本；[JS 执行环境](../crates/flow-engine/src/expr.rs#L261)使用完整 Context，没有固定原生时间和随机数；[准备记录](../crates/flow-executor/src/task.rs#L534)保存 `engine_build` 与 `node_semantics`，但 [build 标识](../crates/flow-executor/src/lib.rs#L13)只是 Cargo 包版本。记录版本字符串不等于按该版本执行。

独立探针验证：

- 同一输入运行 `return {time: Date.now(), random: Math.random()};` 两次，结果不同。
- 父流程 v1 先停在人工节点；此时发布子流程 v2；父流程继续后输出子流程 v2 的结果。

子 run 创建后自身已经保存版本；问题在于父流程启动时尚未形成完整的依赖快照。JS 非确定性也不影响读取已提交的历史结果，但会影响未完成计算的重新求值和重新执行比较。

修复方向：发布或创建 run 时固化依赖清单；记录可识别的执行器产物摘要和语义版本；确定性脚本模式使用持久化的逻辑时间、随机种子，或者拒绝没有受控来源的时间与随机 API。HTTP 和模型响应继续作为外部输入捕获，不能期待相同请求必然得到相同回答。

**4. P1（对直接服务终端用户的承诺）：Webhook 目前只是异步触发器。**

证据：[hook](../crates/flow-rpc/src/journal_triggers.rs#L74)。入口验证全局 Bearer、幂等键和 JSON，返回创建回执。实际成功 HTTP 状态是 200，并非 DESIGN 中写的 202；它不返回流程最终业务结果。已有 RPC 可以查询和订阅 run，不需要再实现另一套执行核心。

全局 token 同时用于管理 RPC 和 hook。如果将它交给普通浏览器业务调用者，就不能区分其调用权限与管理权限。受信任的桌面管理界面可以沿用现状；对外业务接口应采用网关/BFF 或受限 invocation 凭据，将调用者绑定到允许调用的流程和其 run。

建议先补完整异步合同：版本固定的 invocation 入口、输入/输出 schema、业务关联 ID、run 状态/结果、恢复订阅游标、明确错误码和容量拒绝语义。短请求的有限时长同步等待可以以后包在同一 run 之上，超时返回 run 身份，不因客户端断开而重新触发。

另外，[run.signal](../crates/flow-backend/src/journal_commands.rs#L636)只接受已经在 Signal 等待中的节点。先到的回调会被拒绝。需要承接异步回调时，增加按关联身份持久接收、去重、稍后消费的 inbox，或者明确要求调用方重试；不能把这种竞态描述成无缝事件编排。

流程可以实现业务规则并调用业务存储，但 run 状态不承担账户、库存等跨 run 业务实体的完整数据库职责。业务写入需要独立定义事务与幂等边界。

**5. P1（对 LLM 全过程透明的承诺）：harness 目前是一个大黑盒操作。**

证据：[harness_node](../crates/flow-executor/src/task.rs#L1163)。系统记录启动命令、参数、prompt、最终 stdout、stderr 尾部和退出码；这些对恢复非常有用。HTTP 节点也已捕获请求与原始响应。但这并不自动得到模型调用、每次 tool call、工具结果与中间 checkpoint 的结构化记录。

进程内部即使输出 JSONL，Flow 当前也没有据此逐次裁决工具副作用。外层 spawn 获得许可，不意味着其内部每个业务操作都受 Flow 的授权协议约束。

修复方向：定义小而明确的 adapter 契约，记录可观察的模型请求、模型响应、tool call 身份与参数、工具结果、人工批准和完成边界。先接一个能完整闭环的模型/工具适配器。若使用普通 CLI，产品界面要明确其证据粒度是进程级。

仅用于界面展示的 token 流可以走观测面；决定后续工具调用或业务分支的结果，必须先持久提交。记录可观察交互，不承诺恢复模型内部不可见的推理过程。通用 Agent 循环、动态 map、补偿 DSL 等能力应由真实用例驱动，当前不必一起重做。

**6. P2：安全默认值得保留，但所有外部操作都靠人工不能支撑长期自动化。**

证据：[恢复裁决](../crates/flow-backend/src/journal_driver.rs#L449)、[操作授权](../crates/flow-backend/src/execution/dispatch.rs#L1057)、[结果处理与重试](../crates/flow-backend/src/execution/dispatch.rs#L832)。授权后没有 outcome 的操作进入 uncertain；自动重试主要面向 script/condition 的受限场景。HTTP、email、harness 的描述字段却都声明了 `supports_retry`，容易造成比真实能力更强的预期。

把“能否确定性重算”和“能否安全重复调用”分开建模。保留默认人工裁决，并允许适配器显式提供：可重复读取、由对端保证的幂等操作、带业务身份的结果查询。不能仅凭 GET 方法或节点名字推断安全。

使用对端幂等键时，固定逻辑操作身份、请求摘要、作用域和有效期；重试尝试不能产生新键。超出对端去重有效期或无法验证结果时回到 uncertain。人工 retry 仍需提示可能重复业务效果。有关调用方身份与重试语义，可参考 [AWS Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。

**7. P2：日志成为资产，还需要可搬走、可校验和可升级。**

已有能力不是零：[CLI](../crates/flow-cli/src/journal.rs#L8)可以分页导出事件 JSONL 和下载值；[维护工具](../crates/flow-journal/src/bin/flow-journal-tool.rs#L26)有校验、索引重建和一致备份。但事件清单不自动包含定义、全部引用正文、子 run 和运行环境依赖，也不是可直接导入的闭合运行包。

建议新增 run bundle：manifest、定义与依赖、events.jsonl、引用正文、执行环境标识、校验摘要和格式版本。分清完整执行证据与可丢弃 observations；也分清内部完整包和经过脱敏的共享包。脱敏缺失的数据应显式标记，不能仍宣称完整可复现。

当前 [SQLite 读取](../crates/flow-journal/src/sqlite.rs#L43)明确拒绝不同存储格式，[备份](../crates/flow-journal/src/maintenance.rs#L88)也不支持任意历史 LSN 前缀对应的库恢复。这是诚实的开发期边界。开始积累用户资产后，需要格式演进、离线迁移与旧证据读取政策。正常启动不必全量重放历史；损坏时也不应自动覆盖权威库。

DESIGN 不能单独充当现状证据：它还有缺失的 ADR 链接、协议 v5 与代码 v6 的差异，以及与当前 JS BigInt 行为不符的描述。先修正这些契约事实，再讨论更远的架构。

**【Linus式方案】保留权威面，补执行和产品边界。**

```text
业务入口 / 管理入口
        ↓
命令裁决 → 同一个 State::apply → 单次原子提交
                                事实 + 当前状态 + 回执 + 后续动作
        ↓
协调器 → 独立执行器 → adapter
                     ├─ 真实外部调用与结果捕获
                     └─ 回归 fixture，默认禁用外部调用

事实 + 定义 + 正文 → 闭合运行包 → 历史查看 / 回归用例 / 差异报告
```

没有必要先建立庞大的插件系统，也没有必要把调度器、恢复器、回归器各写一套节点执行逻辑。adapter 放在已有实际执行边界，reducer 继续只消费事实。

**HA 的后续方向**

“多控制平面管理多个执行节点”描述了部署拓扑，尚未回答谁有权推进某个 run。现有 [journal_cluster](../crates/flow-backend/src/journal_cluster.rs#L1)明确不保存业务事件、run ownership 或日志副本，不能当作接管基础。

建议路线：当前继续单协调器 + SQLite；需要 HA 时，先做共享事务存储 + 单活协调器接管，执行节点继续独立扩容；协调吞吐确实不足后，再按 run 分区，每个 run 同时只有一个有权提交的 owner。

若选择 PostgreSQL，共享库应在同一事务中保存事件、当前状态、命令回执、待派发动作和 owner 条件。不要采用“PG 只存租约，各控制节点各存本地业务日志”的方案。owner 的 epoch/fencing 条件必须在实际提交端校验，旧结果也要绑定 attempt/dispatch 身份；仅凭心跳和本地 lease 不构成完整 fencing。

HA 保证不能追溯撤回已经发出的外部请求。接管仍须沿用外部幂等、结果核对和 uncertain 规则。数据存储本身的复制、故障切换与可接受数据损失，也应单独明确。这里是后续设计建议，本次没有验证 HA 实现。

另一个应诚实公布的边界：当前全局在飞 dispatch 上限 16，非终态 run 上限 1000，人工等待也计入后者。增加 agent 不会解除这两个上限。没有工作负载与容量数据之前，保留预算，不要直接删除常量。

**可执行中文任务清单（按依赖排序）**

1. **补齐条件分支合流。**

   目标与原因：普通 if/else 的选中路径应能进入公共后续节点，避免无业务输出却报告成功。影响：`flow-engine/src/model.rs`、`journal_state.rs`、`flow-backend/src/journal_driver.rs`、节点描述/UI 及执行 e2e。技术方案：定义 inactive、success、failure 的依赖语义；加入显式 join 策略；全部入边确定后裁决；新定义保存语义版本；明确无有效出口的结果规则。测试：true/false 两方向、并行全成功、失败与未选分支混合、嵌套分支、全 inactive、完成前重启。验收：选中分支的公共后续恰执行一次，旧 AND 流程结果不变。严格约束：禁止全局改 OR，禁止把失败默认为可忽略，禁止重解释旧历史。

2. **固定依赖与执行语义。**

   目标与原因：同一固定版本的运行不能因等待期间发布子流程而改变依赖。影响：流程发布/启动命令、子 run 注册、`Prepared`、executor 身份与 JS 环境，以及新增 manifest 字段。技术方案：新语义的定义在发布时解析子流程版本与摘要，运行继承不可变依赖清单；记录可识别产物的摘要；执行前检查语义兼容性；提供持久逻辑时间/随机种子的确定性脚本模式。测试：本报告的父子版本探针、执行前后重启、依赖缺失、runtime 不兼容、受控时间和随机数重算。验收：固定依赖不随最新发布变化，无法满足的环境显式拒绝；历史读取仍使用录制结果。严格约束：不许拿包版本号代替产物身份，不许声称重新调用模型能精确复现，不静默改变旧脚本语义。

3. **形成闭合运行包与历史还原工具。**

   目标与原因：让一次运行成为可验证、可携带的资产。影响：journal 分页/值读取、CLI 导出、bundle manifest 与离线读取/导入工具。技术方案：固定提交边界，枚举目标 run、已创建子 run、定义和正文的引用闭包；导出 manifest、JSONL 与正文；附摘要、版本和完整性标记；在新目录离线验证、还原工作流状态。测试：大值、子 run、人工信号、缺块、篡改、未知版本、未完成运行的 as-of 边界、脱敏包。验收：完整包在隔离环境不联网即可校验和还原已记录过程；缺失依赖报出明确身份。严格约束：不许把 observations 当恢复依据，不覆盖现有运行库，不把工作流还原说成撤回外部业务效果，不复制出第二个权威写入路径。

4. **实现历史驱动的 regression。**

   目标与原因：将生产运行转为候选流程的可执行用例。影响：新增 baseline/fork/compare 命令、运行来源关系、executor 外部调用边界、CLI 与差异读面。技术方案：创建独立候选 run，引用只读 baseline；共用节点语义；按节点/调用身份及请求摘要匹配 fixture；默认禁网和禁止启动真实 harness；比较节点结果、路径、外部请求、业务断言；允许显式覆盖 fixture，另行定义有预算的 live evaluation。测试：请求改变、调用数改变、分支改变、缺 fixture、大值、对比规则变更、发信/写操作外部调用计数为零。验收：CI 可通过退出码阻止不符合断言的候选版本发布，差异能回指原始证据。严格约束：不修改 baseline，不静默复用不匹配响应，不允许回归模式泄漏为真实业务副作用，不复制 executor 实现。

5. **补齐业务调用合同。**

   目标与原因：让前端能安全、稳定地完成一次异步业务交互。影响：`journal_triggers.rs`、RPC 准入、DTO、流程 schema、命令 scope、可选 inbox 与订阅读面。技术方案：新增版本固定的 invocation 合同，验证输入/输出，返回 run 身份与结果访问方式；用网关或受限凭据绑定调用者、流程和 run；幂等身份包含稳定的授权作用域与请求摘要；支持关联 ID；异步回调先持久接收再消费。测试：重复请求、同键异参、越权读写 run、版本更新、回调早到、重复回调、断线恢复订阅、超限。验收：示例前端可调用、查看进度、提交允许的人工输入并取得结果；业务调用凭据无法管理流程/密钥或裁决他人的 uncertain 操作。严格约束：不把管理 token 分发给普通业务客户端，不把 HTTP 已受理说成业务已完成，不无版本地改变现有 hook 的响应格式。

6. **建立可观察的外部 adapter 与执行策略。**

   目标与原因：透明接入一个 LLM/工具场景，同时减少有安全依据时的人工恢复。影响：`Operation` 数据、请求许可、executor 的 HTTP/harness 执行、模型/工具适配器、节点能力描述与审计事件。技术方案：先实现一个结构化适配器，持久化模型参数、响应、tool call 身份/参数/结果；决策性证据提交后才推进；独立声明非确定性和重复调用安全性；幂等操作固定逻辑 ID、请求摘要、对端 scope/有效期，支持结果核对。测试：流中断、工具执行前后断链、已执行但回执丢失、重复结果、幂等键到期、非幂等写保持 uncertain；回归默认零工具副作用。验收：适配场景的业务决定均能回指持久证据，重试依据在日志可见，能力描述与运行行为一致。严格约束：不从任意 stdout 推断工具成功，不把 LLM 当纯函数，不按 HTTP 方法自动认定幂等，不删除人工裁决默认，不承诺任意外部系统 exactly-once。

7. **确定资产演进与容量合同。**

   目标与原因：已经积累的运行资产应跨版本可读，增长边界应可运维。影响：event/bundle 版本、SQLite 格式与离线迁移工具、DESIGN/OPS、备份与保留流程。技术方案：先明确首个受支持格式；维护黄金历史样本；离线迁移写新目录并比较事实与状态；列明完整证据、回执和 observations 的保留规则；公布 16/1000 限额并按真实工作负载衡量长等待和正文增长。测试：旧格式读取/迁移、迁移中断不损坏源、备份恢复、引用闭包检查、去重身份不复活、容量拒绝可诊断。验收：受支持版本有明确读取或迁移路径，文档与代码契约一致，清理后被保留的证据包仍闭合。严格约束：不静默删旧用户数据，不删除仍被运行/回执/包引用的正文，不为追求吞吐直接解除所有预算；本任务不提前实现 HA 或通用 GC。
